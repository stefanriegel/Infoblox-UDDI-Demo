# Context — Infoblox UDDI Demo

Domain vocabulary for this repo. Terms here name the seams worth keeping.

## Terms

**Allocated subnet**
A next-available subnet drawn from a UDDI IPAM address block and reserved back into UDDI as a `bloxone_ipam_subnet`. The `allocated_subnet` module (`modules/allocated_subnet/`) is the deep module that owns this: it hides the `bloxone_ipam_next_available_subnets` data source, the provider's quoted-string quirk (`replace(trimspace(results[0]), "\"", "")`), the CIDR mask assembly, and the reservation resource. Callers learn one interface — `block_id`, `subnet_size`, `space_id`, `name`, `comment`, `parent_cidr`, `tags` — and get back `cidr` (masked, clean), `address` (bare), `subnet_id`, and `parent_cidr` (passthrough).

Invariant: exactly one subnet is allocated per call (`subnet_count = 1`).

**Cloud-cleanup**
The cloud-side mirror of the `uddi` action. The `cloud-cleanup` composite action (`.github/actions/cloud-cleanup/`) tears down demo VPC/VNet resources across AWS/Azure/GCP behind one `find`/`delete` interface, the same split `uddi` uses. The depth here is **not** a shared predicate — unlike `uddi`'s single canonical `is_demo`, each cloud adapter owns its own discovery filter, because the tag-casing contract in [[adr-0002]] requires it: AWS matches `Demo=true` + `ManagedBy=terraform`, Azure `demo=true`, GCP `description:UDDI`. The adapter also owns dependency-ordered teardown (AWS: detach + delete IGW before VPC; GCP: delete subnets before network; Azure: delete resource group, which cascades). `find` emits a uniform descriptor array (`[{name, id, region}]`, `region` empty off AWS); `delete` consumes it and re-discovers each resource's dependencies at teardown time rather than carrying them through the JSON. Callers (the `cleanup_vpc` job) learn one interface per cloud; the visible job summary in [[adr-0003]] stays, now fed by the action's `deleted`/`failed` outputs instead of inferring success from UDDI subnet presence. Relates to the [[demo-resource]] predicate, which stays UDDI-only.

**Demo resource**
A UDDI resource the cleanup is allowed to delete. Identified by a canonical `is_demo` base predicate — `demo == "true"` evaluated across the three tag schemas the API may return (string value, bool value, or a `[{key,value}]` array). Per resource type, extra conditions layer on: DNS **records** also match a `Terraform-managed` comment (fallback for records that lost their tags); IPAM **subnets** additionally require a known `cloud` tag (`aws`/`azure`/`gcp`), so cleanup never touches a non-demo subnet that merely carries `demo=true`. The base predicate lives in exactly one place — the `uddi` composite action (`.github/actions/uddi/`) — to keep "is this a demo resource?" from drifting between call sites. Relates to the tag-casing contract in [[adr-0002]].

**DNS provider record**
The downstream view of a [[dns-record]] at the cloud DNS provider it was synced to — distinct from the UDDI-side record the `dns_record` module creates. The `dns-provider-record` composite action (`.github/actions/dns-provider-record/`) is the cloud-DNS sibling of the [[cloud-cleanup]] / `uddi` actions: four adapters (Cloudflare via `curl`, Azure via `az`, Route53 via `aws`, Cloud DNS via `gcloud`) behind one interface, all producing the same normalized `dns-record.json` contract — `{provider,found,id,fqdn,type,target,ttl,proxied,provisioning_state,console_url}`. Only the *selected* provider is queried (one writer). Per the run-log-narration precedent in [[adr-0003]], the action emits the per-provider `DASHBOARD INFO` to the run log itself; the `$GITHUB_STEP_SUMMARY` rendering stays in the workflow and reads `dns-record.json` (the management link now reads `.console_url` instead of rebuilding it from secrets). The action owns each provider's console-URL shape, which retired the never-set `AZURE_DNS_ZONE_NAME` bug.

**DNS record**
A single DNS record of any supported type (A, AAAA, TXT, CNAME) in a UDDI authoritative zone. The `dns_record` module (`modules/dns_record/`) is the deep module that owns this: it resolves the zone from its FQDN (hiding the `bloxone_dns_auth_zones` data source and the `.results[0].id` quirk), switches the per-type `rdata` shape (`address` / `text` / `cname`), and selects the created record's id. Callers learn one interface — `zone_fqdn`, `record_name`, `record_type`, `record_value`, `ttl`, `comment`, `tags` — and get back `record_id`, `zone_id`, `zone_fqdn`, and `fqdn`. Replaced three fragmented orphan modules (`record_generic`, `record_cname`, `cf_zone`), one of which passed an FQDN where the provider wanted a zone id.
